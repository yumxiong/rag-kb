# AtlasDesk 接口与异步任务

通过接口接入 AtlasDesk 时，调用方应明确目标工作区、所使用的身份和业务操作。接口请求被接收后，文件处理可能仍在后台继续，因此提交成功和材料可以检索不是同一件事。集成应保存用于跟踪的标识，把请求提交、任务处理和通知接收作为可以分别观察的环节。

## 身份与批量提交

接口调用使用 API Key 进行身份认证。配置时应确认凭据属于预期的团队空间，并按照任务用途安排维护责任。不要把凭据写入知识材料或排查截图。排查认证问题时，可以说明凭据的管理归属和目标空间，但不需要公开实际内容。

批量上传 API 每次请求最多接受 20 个文件。调用方应在发送前完成分组，保持每组材料与业务记录的对应关系。这里限制的是请求包含的文件个数，不能用来推断网页接入中单个文件的大小规则。不同提交路径应分别依据对应说明检查参数。

组织批次时，建议保留原始材料与每次提交之间的关系。某个批次需要重试时，应能找到当时提交的内容，而不是重新扫描目录后得到另一组文件。文件准备、请求构造与结果记录可以分别核对，这样才容易解释失败重试是否仍然代表同一个业务操作。

## 重试约定

重试必须复用相同的 Idempotency-Key，该键有效期为 48 小时；同键搭配不同请求体会返回 HTTP 409。调用方应把键与原始请求内容一起保存，在重试前确认内容没有被替换。键用于识别重复提交意图，不是用于让不同业务操作共用一条记录。

网络中断时，调用方可能无法确定服务是否已经收到请求。此时应先检查已有记录，而不是立即构造一个新的业务操作。若材料确实发生变化，应把变化与原始提交区分清楚。相同文件名也可能对应不同正文，不能仅凭名称判断请求体与上次一致。

## 任务跟踪

异步任务标识用于关联提交后的处理过程。调用方应保存它与原始业务记录之间的对应关系，便于后续查看任务状态。用户看到请求返回，并不代表内容已经进入索引；如果界面需要展示进度，应根据处理信息描述，而不是把提交动作直接标记为全部完成。

任务出现失败时，应保留已有标识和当时的操作背景。不断重新提交可能产生更多需要核对的记录，却不会解释原来的失败原因。排查应先确认材料、目标空间和请求参数是否符合预期，再结合任务信息判断处理停在哪一步。记录中的时间也应使用统一参照，方便关联不同系统中的观察。

## 完成通知

任务完成时发出 job.completed，失败时发出 job.errored。接收方应把通知与先前保存的任务记录关联，确认它对应哪个业务操作，再更新自身状态。通知表达的是任务结果，不能直接替代内容质量审核；材料处理完成后，仍应由维护人员检查关键内容是否适合使用。

接收端的处理逻辑应易于追踪。可以记录通知对应的任务、接收时的处理结论以及本地业务记录是否找到，但不应无差别保存敏感请求内容。对于不能关联的通知，先检查标识保存与查找方式，避免把未找到本地记录直接解释成远端没有执行任务。

## 集成核对

一次完整联调应覆盖材料准备、认证、提交、跟踪以及结果处理。每个阶段都应能说明输入是什么、预期发生什么和实际观察到什么。只检查接收端是否收到消息，无法确认前面的业务内容是否正确；只检查提交返回，也无法证明本地最终记录已经更新。

团队可以用用途明确的示例材料验证流程。示例应包含足够确认提取内容的正文，但不要复制真实工作中的敏感信息。联调人员需要的是可复现的操作条件，而不是完整业务档案。记录排查过程时，也应区分已经确认的事实与仍需验证的猜测。

## 客户端记录

客户端宜保留操作的业务意图，而不只是底层调用结果。例如，一次提交是为了新增主题材料还是整理现有说明，会影响人员如何解释后续状态。业务记录与技术标识相互对应，才能让支持人员在不阅读程序内部实现的情况下，理解当前任务与用户动作的关系。

多个程序参与同一流程时，应先确定各自负责的环节。负责提交的程序需要保存请求信息，负责更新本地记录的程序需要知道如何找到原始业务对象。不要假设它们天然共享相同上下文。交接时应说明数据如何关联，以及出现信息缺失时由谁继续核对。

## 变更检查

调整集成前，建议先列出依赖接口行为的地方。除实际调用代码外，还可能包括任务看板、排查说明和用于演练的材料。修改代码后应检查这些描述是否仍与当前流程一致，否则使用者可能依据旧说明判断问题，导致实现已经更新而排查路径仍然停留在过去。

回归检查应关注完整业务结果，而不是单个函数有没有执行。可以从一份已知材料出发，跟踪它进入系统后各项记录如何变化，确认中间标识没有丢失。若某个阶段的记录无法与前一步关联，应先修复这条关联，再判断是不是后台处理本身出现异常。

上线后的观察也应有明确对象。需要检查的是新流程是否按预期处理，而不是只看整体任务数量有没有变化。历史积压、手工重试和新提交可能同时出现在记录中，混合统计会掩盖实际问题。将它们按业务来源核对，更容易说明某次调整带来的影响。

维护文档时，应把当前集成路径写在正常操作说明中，把仅用于理解历史记录的信息放在明确标记的附录。读者不应依靠猜测来判断某条说明是否还适用。查看旧记录时也应保留其原始背景，避免按照今天的实现方式重新解释过去的流程。

## 交接演练

交接程序给其他维护人员前，可以让接手者根据说明完成一次演练。演练应能从业务任务找到提交记录，再找到对应的后台处理结果。如果某一步只能依赖原作者的记忆完成，就说明文档仍有需要补充的地方。补充应解释信息之间的关系，而不是简单增加一串没有用途说明的日志内容。

演练中出现差异时，应先记录使用了哪些材料和配置，以及观察结果与预期有什么不同。不要立即把差异归因于接手者操作不熟悉。它也可能暴露了程序对本地目录、旧记录或隐含环境条件的依赖。将这些前提写清楚，能减少之后部署和排查时的重复沟通。

维护人员还应知道哪些资料用于当前操作，哪些只供历史核对。把历史片段当作现行配置，可能让新接入重新引入已经调整的行为。团队可以在交接时检查说明的入口顺序，确保正常操作章节容易找到，历史内容保留明确背景。清楚的文档组织本身也是接口维护的一部分。

## 旧集成附录

早期集成接收 document.done，该旧通知已弃用，相关客户端必须迁移。此处仅用于识别历史记录，不应作为新接入的实现依据。变更背景与迁移关系见发布说明；维护人员应根据当前接口章节检查接收逻辑，而不是把旧日志中的名字直接复制到新的配置里。

检查遗留实现时，可以先梳理仍在使用的处理入口及其业务用途，再确认哪些历史说明需要归档。旧资料应保留明确的历史标记，使接手人员知道它解释的是过去的行为。完成迁移后，也应核对团队排查说明，避免有人继续依据历史通知判断新任务是否结束。
