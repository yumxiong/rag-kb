# AtlasDesk 配额与计费

AtlasDesk 的用量规则按操作和范围分别定义。检索请求、程序上传、材料索引和生成式问答并不共享同一个计量含义。查看限制前，应先明确自己正在执行什么操作，以及限制是面向团队空间、调用凭据还是月度材料用量。只记录一个数值而没有范围，容易让排查人员把不同规则混在一起。

团队规划用量时，可以先整理主要工作流程。日常成员搜索资料与自动化程序集中提交材料具有不同的节奏。一个流程频繁请求，并不意味着另一个流程的额度也被耗尽。把操作目的和出现时间一起记录，有助于在观察到请求受限时找到实际原因，而不是盲目调整所有客户端。

## 请求频率

| 操作及套餐 | 限制 |
|---|---|
| Standard 搜索 | 120 次/分钟/工作区 |
| Enterprise 搜索 | 600 次/分钟/工作区 |
| 上传 API | 10 次/分钟/API Key |

搜索限制的统计对象是团队空间，上传接口的统计对象则是调用凭据。排查时应先确认受到限制的操作，再检查是否有其他程序或成员同时使用相同范围。单个客户端看到自己调用不多，并不能由此断定整体范围内没有其他请求。团队协作与自动化任务可能在同一时间产生用量。

程序应避免在失败后立即无间隔地重复相同操作。集中重试可能让请求更密集，也会让排查记录出现大量重复现象。更有帮助的做法是识别受限阶段，按照对应的处理说明等待后再继续，并记录实际发生的变化。等待策略应与业务任务安排一起考虑，避免多个程序同时开始重复提交。

观察请求节奏时，可以将人工操作和自动任务分别整理。某个整点开始的集中任务可能使短时间请求明显增多，但这不等于全天都处于相同状态。先理解任务来源，再决定是否需要分散操作时段。增加调用凭据也不能被当作绕过其他范围限制的通用办法。

## 月度索引额度

月度索引页配额为 Standard 5,000 页、Enterprise 100,000 页，每月首日的 00:00 UTC 重置。这个规则用于月度材料索引用量，不是每次搜索能够读取的页数，也不是文件处理完成所需的时间。团队检查月末任务时，应使用同一时间参照理解边界。

准备一批材料时，应把索引用量与请求组织方式分别考虑。文件份数、正文页数以及程序发出的请求数属于不同概念，不能互相直接替换。把许多材料合成一份文件并不意味着正文规模随之减少。核对配额时应回到相应计量对象，而不是仅观察上传界面中的文件列表。

月度安排适合结合内容维护计划制定。经常重复整理相同主题时，可以先核对现有材料是否已经覆盖需要，再决定是否接入新的内容。为了赶在月末提交而省略资料审核，可能让后续维护成本增加。用量规划应服务于知识库质量，而不是让团队只关注额度是否被用完。

删除资料与月度边界属于不同规则。需要同时了解内容移除和用量安排时，应分别查阅保留策略与本节说明，不能凭一个操作界面的变化推断另一项计量结果。尤其在任务跨越月末时，应记录提交背景和观察时间，保证讨论针对同一阶段的信息。

## 自带模型的账务范围

BYOK 移除 AtlasDesk 的生成 token 费用，但不会免除索引页配额。它影响生成式问答中模型用量的账务范围，不会让文档接入与检索前的材料准备脱离原有规则。评估成本时，应把生成环节和索引环节分开核对，避免把一种费用变化解释成全部用量都不再受约束。

负责选型的成员需要了解团队主要使用哪些功能。如果大量工作集中在整理材料，单独改变生成模型安排不一定解决接入规模问题。若主要关注生成环节，则应结合实际问题与输出需求进行评估。讨论时明确每个环节的用途，可以减少以局部变化推算整体成本的误差。

模型配置与套餐开放范围也需要分别确认。是否允许使用某项功能，由产品与套餐说明定义；使用后影响哪些计量项目，则由对应账务说明定义。两者共同决定实际使用方式，但不能互相代替。团队可以在选型记录中列出这些问题，供配置和维护人员逐项检查。

## 用量异常排查

遇到用量与预期不同的情况，应先明确观察来源及计量范围。一个看板展示的是任务数量，另一个记录的是材料页数，它们不相等并不必然表示统计异常。排查人员需要知道所比较的数字代表什么，才能决定是否存在实际问题。没有范围的截图通常不足以完成判断。

建议先选取一段业务活动较清楚的时间，核对当时执行了哪些操作，再检查相关用量信息。重试、手工补交和计划任务都可能造成与最初估算不同的实际活动。核对过程应围绕这些具体事件展开，而不是直接从总体变化推断某个组件有误。

保存排查材料时，应去除凭据正文以及与问题无关的内容。可以记录操作类型、所属团队空间和时间参照，让负责人员定位相关用量。对于仍未确认的原因，应标记为待核对，避免猜测被后续人员当作已经确认的规则继续传播。

## 估算与观察

开始估算之前，应先列出团队真正需要执行的操作。资料整理频率、自动任务的触发方式和成员查阅习惯，都可能影响实际用量。估算不是一次填写后永久有效的数字，而是用来与后续观察比较的起点。记录估算依据，可以让团队知道出现偏差时应该检查哪个假设。

观察期间应保持计量对象一致。如果前一次记录的是某类任务，后一次却包含了其他工作，就不适合直接比较总体变化。可以先解释新增活动，再判断原有流程是否发生异常。这样的分析能够区分正常业务增长与非预期重复操作，也避免把任务来源变化误认为平台计量规则改变。

对于没有足够记录支持的估计，应明确其不确定性。可以先安排一次可观察的小范围操作，确认数据含义后再扩大使用。没有必要为了给出一个整齐数字而隐去未知条件。清楚说明目前已知什么、仍需核对什么，能帮助负责选型和实际维护的人员形成一致预期。

## 计划维护

用量规划不必一次覆盖所有未来场景。先从当前明确的资料维护和查询需求出发，记录实际活动，再逐步修正估算。团队扩大或接入方式变化后，应重新检查哪些环节成为主要用量来源。原先适用于少量手工操作的安排，未必适合自动化任务集中运行后的节奏。

交接时应说明各项限制的适用对象和团队目前如何安排任务。只交付一张数值表，接手人员可能不知道哪些操作会影响它。把真实工作流程与计量范围联系起来，才能让后续成员在看到异常时知道先检查什么，也便于团队解释一次配置调整是否解决了原来的问题。
