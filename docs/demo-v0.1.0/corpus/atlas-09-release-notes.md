# AtlasDesk 发布说明

本页按从新到旧的顺序记录与现有使用方式有关的变化。历史条目用于解释过去的行为，不能直接替代当前操作说明。维护集成时，应先明确依赖的功能和原有预期，再沿对应条目核对调整。对于没有在这里列出的细节，应回到当前功能文档确认，不要从历史描述推导额外规则。

## v2.0

当前发布整理了面向团队协作的使用说明，将资料接入、检索和管理职责分开解释。维护人员可以按照操作阶段寻找相关约定，避免把不同范围的限制混在一起。本条目描述当前说明的组织方向，不改变各功能章节中已经明确的适用条件。

升级检查应围绕实际工作流程进行。先选择团队经常执行的操作，确认资料准备、提交跟踪和检索使用是否仍与预期一致。不要只检查页面能够打开，就认为所有集成都已经完成验证。对于依赖自动化的团队，还需要核对本地记录如何与后台处理结果关联。

团队更新内部说明时，可以把当前操作入口和维护责任放在易于查找的位置。旧截图或历史排查过程可能仍有参考价值，但应标记其背景。新成员需要知道哪些内容描述当前使用方式，哪些只是解释过去出现的问题。清楚区分这些材料，有助于减少接手时的误解。

## v1.9

本次将 webhook 事件 document.done 更名为 job.completed。维护旧接收端时，应更新事件识别及其关联说明，并核对本地业务记录是否仍能正确接续。历史事件记录可以用于解释过去的处理，但不应作为新集成选择名称的依据。失败通知的当前约定见接口文档。

接收端改动不只是替换一个字符串。维护人员还应检查测试材料、排查说明和用于展示任务结果的本地逻辑，确认它们对完成通知的理解一致。若某些记录无法找到对应任务，应先核对标识保存与查找方式，再判断是不是通知处理发生问题。

迁移演练可以从一份用途明确的示例材料开始，完整观察提交后各项记录的变化。示例不需要包含真实业务信息，但应能够让验证人员确认它对应同一次操作。完成演练后，记录使用的配置背景与观察结果，供其他维护人员复核，而不是仅保留一个“已迁移”的结论。

## v1.8

本次将最终返回结果的默认值从 8 条调整为 6 条。旧集成如果依赖固定的列表长度，应检查自身展示与后续处理方式。这里记录的是最终输出默认值的变化，不是前置检索各阶段的输入规模；当前候选处理流程应以检索与生成文档为准。

检查客户端时，应找出哪些地方把默认结果长度当成了固定业务条件。例如，界面是否假设每次都填满一组展示位置，后续处理是否直接按旧长度读取列表。理解这些依赖后，再判断需要调整的是展示逻辑还是操作预期。不要仅看到结果减少就推断材料没有进入搜索范围。

变更后的验证应使用相同的问题与资料，观察最终列表及引用内容。数量变化不直接说明相关性提高或降低，仍需检查结果是否覆盖问题所需的证据。可以保留有代表性的案例，说明客户端在不同列表长度下如何工作，以及维护人员确认了哪些行为。

## v1.7

这一历史阶段的维护说明强调了接入过程与任务结果之间的关联。集成方需要能够从业务操作找到相应处理记录，避免只保存一次提交的成功提示。接手旧程序时，可以先检查其是否保留了这种关联，再决定后续如何整理跟踪与排查方式。

历史程序可能由多个独立脚本逐步扩展而来。一个脚本准备材料，另一个负责提交，后续还有程序更新业务状态。每个部分单独执行正常，并不保证它们之间的信息完整。核对时应沿着一项具体业务操作检查，确认标识、目标范围和处理结果能否逐步对应。

整理旧流程时，建议把观察到的实现与团队希望达到的行为分别记录。有些步骤可能只是过去应对临时问题的安排，后来却被反复沿用。理解它最初解决的问题，可以帮助判断是否仍需要保留。没有明确用途的步骤不应仅因为存在很久，就被视为不可改变的规则。

回顾历史问题时，还应检查当时材料的背景。旧说明中的某个异常可能与特定接入方式有关，不能直接套用到所有操作。负责维护的人应说明案例涉及哪个阶段、如何观察以及哪些条件已经确认。这样保存的记录才便于后来的人判断它是否适用于新问题。

对旧集成进行整理时，可以先从可复现的例子出发，而不是一次替换全部逻辑。逐项确认输入、记录关联和最终结果，有助于发现隐藏的依赖。需要修改时，也应保留验证范围，让团队知道哪些部分已经检查过，哪些仍需要在后续任务中继续观察。

维护说明应随实际检查结果更新。若原文缺少适用条件，可以补充背景；若排查过程只是一次临时猜测，则应标明它没有被确认。历史知识的价值在于帮助理解，而不是让每条过去写下的话都成为当前约束。清楚记录证据，能减少后续人员重复走过相同的排查弯路。

迁移过程中产生的新说明也应保持同样标准。不要只写“兼容旧版”而没有指出验证了哪些流程。可以列出实际使用的材料类型、业务动作和观察结果，但不需要复制敏感配置。对仍有不确定性的地方，应说明下一步核对方向，使交接人员能够继续完成工作。

迁移结果需要与团队实际使用的流程联系起来。某次验证只覆盖手工提交，就不能据此断定所有自动任务都已经检查。可以先把已覆盖的路径记录下来，再根据实际需求安排后续检查。说明验证边界能帮助接手人员正确理解进度，也避免因为一个成功案例而忽略其他仍需确认的环节。

对于暂时保留的历史依赖，应记录保留原因及后续检查方向。它可能仍被某个旧程序使用，也可能只是文档没有清理。明确用途后再决定如何处理，比简单删除所有旧说明更容易保证维护连续性。历史材料与当前说明可以同时存在，但两者的范围应让读者一眼能够识别。

团队在回顾时可以选择一个已完成的迁移案例，检查从发现差异到确认结果的记录是否完整。若关键判断只存在于个人记忆中，应补充到维护说明。这样积累的经验能够帮助下一次调整，而不只是证明过去曾经做过一次工作。清晰的过程记录也便于后来人员判断新问题是否与旧情况有关。

## v1.6

在这一历史版本中，向量搜索默认返回 8 条结果。这是旧行为记录，仅用于理解当时的集成预期，不能作为当前流程的默认规则。维护旧客户端时，应回看它依赖的展示和处理方式，并结合较新的变更条目确认是否需要调整。

历史结果列表可以帮助解释旧截图与旧记录，但不能直接拿来判断今天的检索是否异常。两次观察之间可能不仅有默认设置变化，也有材料或查询范围变化。比较时应先固定这些条件，再讨论差异来自哪里。缺少操作背景的截图不适合单独承担结论依据。

团队保留旧条目时，应确保读者能够看出它属于历史范围。新接入人员应从当前功能说明开始，再按需要了解迁移背景。这样既保留了维护旧程序所需的信息，也能避免把已经调整的默认行为继续带入新的实现和培训材料。
