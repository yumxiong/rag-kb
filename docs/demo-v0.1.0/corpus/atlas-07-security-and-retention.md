# AtlasDesk 安全与保留

AtlasDesk 的安全管理同时涉及内容边界、人员职责和材料处理。团队应先确定哪些资料适合放入内部知识库，再决定维护方式。技术控制不能替代内容审核，能上传的文件也不意味着应该向所有协作人员开放。整理材料时，应主动去除与业务知识无关的身份信息和凭据。

## 删除与恢复

删除文档后，其内容立即离开索引；源文件在回收站保留 7 天，期间可以恢复。搜索范围的变化与原文件的保留阶段需要分别理解。成员发现删除后的材料不再出现在搜索结果中，并不能据此推断源文件已经无法找回。需要恢复时，应依据该阶段的规则处理。

执行删除前，建议先确认材料的用途和负责人员。有些说明可能仍被其他团队成员用于日常工作，仅凭近期没有更新不能判断它已经失效。可以先核对是否存在替代材料、哪些读者会受到影响，再按团队约定执行操作。处理完成后，也应让相关人员知道内容范围已经发生变化。

删除说明适合记录业务原因和处理对象，不需要复制文件中全部正文。若操作是为了解决资料错误，应同时说明正确内容将由谁维护，避免旧材料移除后留下知识空缺。恢复旧材料时也应重新检查适用条件，不能因为文件能够找回，就认为其中规则仍然符合当前业务。

## 存储位置

数据区域在创建工作区时选择，创建后不能更改。团队应在建立空间之前确认位置要求，再开始组织成员和材料。这个选择属于空间建立时的规划事项，不能依靠后续修改资料标题或调整知识库分类来改变。需要不同位置安排时，应先重新评估团队结构和资料处理方案。

做位置规划时，可以列出材料来源、阅读对象及内部管理要求，供负责人员确认。不要仅因为另一个团队曾经采用某种安排，就直接照搬其决定。不同资料和协作关系可能对应不同需求，规划过程应围绕当前团队的实际情况展开，并保留足以解释选择依据的记录。

## 加密与配置管理

传输和存储中的内容需要结合平台加密措施与团队配置管理共同保护。成员不应通过共享个人凭据来完成协作，也不应把连接信息直接放入面向读者的操作说明。知识材料可以解释如何申请或管理配置，但不应包含能够直接访问系统的秘密内容。

排查安全相关问题时，应先区分内容暴露、身份配置和操作记录等不同对象。一个成员看到了不适合其职责的材料，可能需要检查团队权限与内容组织；程序使用了错误凭据，则需要检查自动化配置。将所有情况都称为安全故障，会让处理人员难以确定具体检查范围。

团队可以为配置变更建立清楚的交接约定。交接材料应说明用途、维护责任和核对方式，而不必复制凭据本身。发现配置用途已经变化时，应及时让相关人员确认新的范围，避免一个为临时任务准备的安排在无人知情的情况下长期使用。记录清楚的职责也有助于后续排查。

## 内容检查

上传前的检查应关注材料是否包含与知识用途无关的信息。真实工作记录可能混有个人身份、访问凭据或其他不适合进入共享内容的部分。维护人员应提取能够解释规则的内容，并使用不涉及真实对象的示例说明操作过程。资料的价值在于帮助理解业务，而不在于保留原始记录中的每个细节。

检查不能只依赖关键词。某些片段即使没有直接出现姓名，也可能通过上下文暴露具体对象。对于排查材料，应保留解释技术现象所需的信息，去除与判断无关的细节。经过整理的记录更便于团队讨论，也减少后续分享时反复判断哪些部分需要遮挡的成本。

资料更新后，也应重新检查新加入的示例与附注。原文经过审核，并不意味着后续每次补充都自动满足相同要求。尤其是从临时讨论中复制的处理过程，可能夹带当前任务的私人信息。把内容检查纳入正常维护流程，比等到准备分享时再集中清理更容易保持一致。

## 记录阅读

操作记录用于帮助理解发生过什么，而不应被当作所有业务背景的完整替代。阅读记录时，应结合操作对象、人员职责和当时的工作安排。一个动作的存在能说明有人执行过操作，但未必说明业务上为什么这样决定；需要进一步理解时，应寻找相关维护说明。

团队讨论记录时也应限制到实际问题范围。排查某次资料处理，不必向所有参与者展示其他不相关活动。可以先明确需要确认的事实，再选择相应记录进行核对。负责人员应区分已经观察到的操作与对操作目的的推测，避免把未经确认的解释写入后续结论。

## 共享前的复核

准备把内部处理经验整理成知识材料时，应再次检查示例是否确实需要保留原始对象。多数操作规则可以用虚构的名称和经过整理的内容说明，无需把真实事件的全部背景带入知识库。复核应关注读者理解规则所必需的信息，避免因追求案例完整而保留不相关细节。

跨团队讨论安全问题时，应先说明讨论目标和需要确认的事实。不同人员可能只负责其中一部分工作，不一定需要看到全部记录。提供经过整理的上下文，通常比直接转发完整材料更容易聚焦问题。对已经去除的细节，也应确保没有通过其他字段的组合重新暴露出来。

复核完成后，可以记录采用了哪些处理方式以及仍需注意的范围。这些记录用于帮助后续维护人员理解内容为何这样组织，不应被当作永久有效的保证。材料发生变化后仍需要重新检查，特别是加入新的示例、截图或排查片段时。内容管理依赖持续维护，而不是只在首次上传前进行一次确认。

## 操作留痕

审计事件在 Standard 保留 90 天，在 Enterprise 保留 365 天。保留范围用于查询历史操作，不等同于已删除源文件的恢复期限。需要回看较早的管理动作时，应先确认当前套餐对应的记录窗口，再判断所需信息是否仍在范围内。不同对象的保留时间不能互相替代。

核对历史操作时，应先确定需要查找的对象和时间背景。若只有模糊的“以前发生过”描述，负责人员很难确认记录是否覆盖该事件。可以结合团队交接说明缩小范围，但不要把人的记忆直接当作记录内容。查询结果与业务解释应分别保留，便于他人复核。

## 维护责任

安全与保留安排需要有人持续解释和维护。团队结构变化后，应重新确认谁负责内容检查、谁处理删除恢复问题、谁核对历史记录。不同职责可以由同一个人承担，但其工作范围仍应清楚，避免成员遇到问题时不知道应从哪一项规则开始询问。

日常回顾可以选取具体操作案例，检查资料是否按预期移除、恢复流程是否被正确理解，以及查询历史记录时是否使用了正确范围。通过实际案例核对规则，有助于发现文档中不够清楚的地方。改进应回到操作说明和团队分工，让后续人员能够依据明确约定开展工作。
